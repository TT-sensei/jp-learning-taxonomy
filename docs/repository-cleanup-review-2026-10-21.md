# リポジトリ整理・README更新記録（2026-10-21）

## 今回の方針

README が長くなり、同じ話題が何度も現れるうえ、過去の作業時点の件数・状態・「未確認」という説明と、その後に追加された監査結果が混在していた。入口の README は「何のプロジェクトか」「どこを見ればよいか」「今どこまで確認できたか」「どう検証するか」に絞り、経緯は日付付きの監査記録に残す。

## 実施したこと

- ルートの README を短く再構成した。
- 現在のデータ・検証スクリプト・学習マップ・出典・ライセンスへの入口を整理した。
- 公式コードについて、コードの存在確認と意味的な対応確認は別だと明記した。
- 過去の件数を README に固定値で書き並べず、最新の対応表と監査記録へ誘導するようにした。
- 古いレビュー記録を削除せず、作業履歴として扱う方針を明記した。

## ファイルの扱い

### 維持する（現在の役割がある）

- `data/topics.json`、`data/dependencies.json`：サイトが使う共通データ
- `data/curriculum-standards.json`、`data/curriculum-code-mapping.json`：出典とコード対応状況
- `data/manifest.json`、`schema/`：データセットの説明と形式
- `scripts/validate.mjs`、`scripts/check-official-curriculum-codes.mjs`：検証の再現性を保つ
- `.github/workflows/`：自動検証
- `site/`、ルートの `index.html`：公開サイトの入口と画面
- `LICENSE`、`LICENSE-DATA.md`、`PROVENANCE.md`：利用条件と出典管理
- 教科別草案・監査記録：現在の候補を説明し、判断の根拠を追跡するために維持

### すぐには削除しない（依存関係の確認が必要）

- 日付付きの古い監査・レビュー記録
- `*-draft`、`*-review`、`*-audit` といった草案・作業記録
- 算数の分割提案・移行設計ファイル
- 旧 ID や superseded 項目を含むデータ

これらは古い・重複して見えても、現在の ID、リンク、移行記録、監査の根拠として必要な可能性がある。削除する前に、JSON 参照、Markdown リンク、スクリプト、公開ページからの参照を検索する。

### 次の整理で確認すること

1. すべての Markdown リンクのリンク切れ。
2. README と manifest の項目数・関係数・教科別件数の一致。
3. 古いメモにしか残っていない決定事項や、現行データと矛盾する説明。
4. 同じ内容を重複して記録した文書を、最新の一覧から過去の記録へリンクする形に整理できるか。
5. 未参照の JSON・HTML・画像・スクリプトを洗い出し、公開サイト・GitHub Actions の参照がないことを確かめてから削除候補にする。
6. README の記述と実際の検証手順が一致するか、GitHub Actions で再確認する。

## 削除判断のルール

名前が古い、草案である、日付が古いという理由だけでは削除しない。依存関係を確認し、現行データに取り込まれたことを確認できた場合も、監査履歴として必要かを判断する。削除する場合は、対象と理由を記録し、まとまった変更単位で実施する。

## 検証ステータス

この記録の作成時点では README を更新し、整理方針を明文化した段階。リポジトリ全体のリンク切れ検査、未参照ファイルの機械的な検査、公開サイトのブラウザ確認はまだ完了扱いにしない。
